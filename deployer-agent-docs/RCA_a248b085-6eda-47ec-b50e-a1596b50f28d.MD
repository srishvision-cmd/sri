# RCA — `insurance-mis-portal` — POST /api/policies/upload fails in production

## Symptom
On the live app, every file on the Upload page fails ("Upload failed") when an admin uploads 5 PDFs of ~1.6 MB each. The same multipart request succeeds in preview with a small PDF (200 OK).

## What the production logs show (active run `a248b085-6eda-47ec-b50e-a1596b50f28d`, tier_0, deployment-cluster-03)
- **The backend process restarted repeatedly during the failure window.** Fresh startup sequences appear at:
  - `2026-10-10 09:54:21` → `Object storage initialized` → `Uvicorn running on http://0.0.0.0:8001` → `Started server process [24]`
  - `2026-10-10 10:29:57` → same sequence → `Started server process [23]`
- **Each restart is immediately preceded by a sustained flood of health-probe failures** against the backend upstream, e.g. from `10:28:12` through `10:29:56`:
  - `nginx [error] ... upstream timed out (110) while reading response header from upstream ... request: "GET /health" ... upstream: "http://127.0.0.1:8001/health"`
  - then `connect() failed (111: Connection refused) while connecting to upstream` (backend fully down) at `10:29:56`, followed by the fresh process start at `10:29:57`.
  - An identical window occurred at `09:54` (`connect() failed (111: Connection refused)` on `/api/policies`, `/api/agents`, `/health`) just before process [24] started.
- **No HTTP 413 and no application 500s** were captured for `/api/policies/upload` in the window — the failures are gateway-level (backend unreachable/timeout), i.e. the upload connection is dropped when the pod is killed/restarts.
- `preview_health_check` on `/health` currently returns 200 but in **1520 ms** for a trivial endpoint — evidence the backend is under heavy CPU pressure even outside the worst windows.
- A single `Traceback (most recent call last):` was present in logs; its body could not be retrieved (truncated) and it is secondary to the dominant restart-under-load pattern.

## Tier / resource ceiling
`get_tier`: tier_0 "Starter" — **cpu_limit 250m (¼ core), memory_limit 512Mi**, 2 replicas, single uvicorn worker (`uvicorn server:app --workers 1`).

## Root cause
The recent change to `lib/compress.py` runs `doc.subset_fonts()` and `tobytes(use_objstms=1)` on every uploaded PDF. Font subsetting is extremely CPU- and memory-intensive. Even though it runs in `asyncio.to_thread`, the work still consumes the container's CPU; on a 250m (¼-core) limit, processing 5 × ~1.6 MB PDFs saturates CPU (and pressures the 512Mi memory limit). The uvicorn event loop then cannot answer the Kubernetes liveness probe hitting `/health` within the probe timeout (nginx proxies `/health` with a 1s read timeout). The probe fails repeatedly, Kubernetes kills and restarts the backend container, and any `POST /api/policies/upload` in flight is dropped — surfacing as "Upload failed" in the UI for all files.

Preview has no CPU/memory limits and was exercised with a single small PDF, so the expensive path never saturates resources there — which is why it returns 200 in preview.

## Confidence / caveat
- High confidence that the failure mode is **backend restart / unresponsiveness under the new PDF-processing load**, based on the tight correlation between the `/health` timeout floods and the subsequent fresh `Started server process` lines, plus the slow live `/health` response.
- **Not independently confirmed:** the exact kill reason (OOMKilled exit-137 vs liveness-probe kill). `get_pod_events` failed with `cluster deployment-cluster-03 not found`, so container `last_termination` could not be read. Either way the trigger is the new CPU/memory-heavy compress path exceeding what tier_0 can serve while staying responsive.
- Not reproduced in an eph sandbox: the sandbox is given more CPU/memory than production, so a CPU/memory-saturation restart would not reproduce there.

## Recommended fixes
1. **Code (primary) — `lib/compress.py` / upload endpoint:** make the heavy font-subsetting resilient and bounded so it cannot take the process down:
   - Skip / make `doc.subset_fonts()` optional (it is the most expensive operation) or gate it behind a size threshold; `tobytes(use_objstms=1)` alone is far cheaper.
   - Process PDFs **sequentially with a concurrency limit of 1** (an `asyncio.Semaphore`) rather than fanning out all 5 at once, to avoid CPU/memory spikes that starve the health endpoint.
   - Add a per-file size/time cap and wrap compression in try/except so a failure degrades to storing the original PDF instead of crashing the request.
2. **User (contributing) — tier:** tier_0 gives only 250m CPU / 512Mi memory. Even with the code fix, this workload benefits from more headroom; raising the tier in Deployment Panel → Resources reduces the chance of probe-kill restarts under concurrent uploads. (Stated as contributing, not independently confirmed as the sole cause since pod termination state was unreadable.)

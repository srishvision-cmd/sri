## THE EXACT REASON NO OTP IS SHOWN (root cause)
**No OTP claim is ever created, because `POST /api/otp/request` never reaches the backend.**
- The `otp_claims` collection **does not exist** in DB `insurance-mis-portal-app` (mongo `count` → `collection_not_found`; existing collections: brokers, status_checks, commission_rules, insurer_portals, users, portal_views, app_state, agent_groups, commission_statements, policies). The collection is created on first `insert_one` in `request_otp`; its absence means that insert has **never** succeeded.
- Backend logs for the active run over the last 180 min contain **zero** `POST /api/otp/request` lines. We DO see the page polling: repeated `GET /api/otp/messages` 200 and `GET /api/otp/mailbox` 200, plus `GET /api/portals`, `PUT /api/portals/bfd84fef...` 200, auth/stats. No OTP request POST at all, and no 4xx/5xx on that path (so it is not reaching the server and being rejected — it is simply not arriving).
- Consequence in code: `otp_messages()` runs `claims = db.otp_claims.find(...)` → empty → `mine = []` → `if not mine: return OtpFeed(messages=[])`. The function returns an empty feed **before** any mailbox read, filter, or timing logic. So IMAP/filters/skew are all moot while there is no claim. UI shows "No OTP request running."

The frontend IS wired correctly (frontend/src/pages/Portals.tsx:121-146): the "Get OTP" button calls `getOtp.mutate()` → `apiPost("/otp/request", { portal_id: p.id })`. Since the source wiring is correct but the POST never lands on the backend, the break is client-side at request time — most likely a **stale cached JS bundle after the redeploy** (frontend is kubernetes/nginx-served) or a runtime JS/auth error swallowing the click — OR the user did not actually trigger it within the observed window. This must be confirmed from the browser Network tab.

## Most probable root cause (needs source-level confirmation by E1)
The log signature — `/purge/preview` fires and returns 200, but the real `POST /purge` delete is **never sent** — together with "data + types are correct in prod" points to one of two source-level causes:

**(A) Backend date-window logic returns 0 matches despite matching data.** The `[date_from 00:00 IST, date_to+1 00:00 IST)` bounds are computed in Python in `backend/routers/rule_purge.py`. Candidate bugs: IST offset / `ZoneInfo("Asia/Kolkata")` resolving differently in the prod container, tz-aware vs naive datetime mismatch when building the `$gte/$lt` bounds, or an off-by-one on `date_to+1`. If preview returns `matched=0`, the frontend never arms the delete → no POST (matches the logs exactly).

**(B) Frontend arming/gating in `frontend/src/components/PurgeRules.tsx`.** Even if preview returns rows, the "confirm/delete" button may fail to arm (e.g. `confirm_count` wiring, response-shape mismatch between preview payload and what the delete expects), so the POST is never issued.

(A) is the stronger candidate given the log pattern.
